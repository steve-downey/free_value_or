* Provenance

- P2988R12 (optional<T&>), Design / value_or: "no particularly wonderful
  solution for value_or that does not involve a time machine."
  optional<T&>::value_or returns remove_cv_t<T> by weak consensus, and the
  paper promises free functions ~reference_or~, ~value_or~, ~or_invoke~, and
  ~yield_if~ over a nullable/maybe concept "in the next revision of P1255".
  This paper is that follow-on, extracted to its own number.
- P3199R0 / homework-tokyo.org has the implementation survey and the
  common_reference formulation. Reuse the divergence table:
  | Impl       | Behavior                                               |
  |------------+--------------------------------------------------------|
  | Standard   | optional<T>::value_or returns a T                      |
  | Boost      | optional<T>::value_or returns a T                      |
  |            | optional<T&>::value_or returns a T&                    |
  | TL         | optional<T>::value_or returns a T                      |
  |            | optional<T&>::value_or returns a T                     |
  | Flux       | returns result of ternary, similar to common_reference |
  | Think-cell | returns common_reference, with some caveats            |
- P1255R13 (views::nullable) defines the nullable concept this paper
  constrains on, and its R13 history already lists "Free functions on maybe
  types such as optional and pointers". R0 must explain the extraction to a
  new number rather than a P1255R14.
- P3413R0 "A more flexible optional::value_or (else!)" (Jabot, 2024-10),
  reviving P2218R0 (Mutz, abandoned): member value_or_construct (lazy
  in-place fallback, init-list overloads) and value_or_else (lazy callable)
  on optional and expected; return type stays T, no references, no
  pointers, optional<T&> deferred to P2988. Fixes the *cost* of the
  alternative where D4270 fixes the *type* and the *reach*. R0 of this
  paper carried a "Relation to P3413R0" chapter treating it as adjacent;
  LEWG in Brno (2026-06) asked for one proposal, and R1 is it: Corentin is
  co-author, the members are the paper's member half, and the chapter is
  now "P3413R0, and the two halves". optional<T&> is specified rather than
  deferred, being C++26. Also relevant: LWG3886 (Monad mo' problems), left
  out of P3413.

* Thesis

value_or has two defects, and R1 carries the fix for each.

The type: optional<T>::value_or's return type (remove_cv_t<T>) is wrong and
unfixable in place. The correct return type is computed from the
dereferenced type and the alternative — common_type for values,
common_reference for references — machinery younger than std::optional.
Free functions constrained on ~nullable~ fix the computation and
generalize to all pointer-like types: optional, expected, raw and smart
pointers, optional<T&>.

The cost: the alternative is an ordinary argument, built whether or not it
is used. A new member name fixes that in place on the types that have
members: value_or_construct and value_or_else, from P3413R0.

* Current interface (include/beman/free_value_or/value_or.hpp), R1

#+begin_src c++
template <class T>
concept nullable = requires(const std::remove_reference_t<T>& t) { bool(t); *(t); };

// The type *m yields, value category of the nullable carried through.
template <class T>
using deref_t = decltype(*std::declval<T>());

template <nullable T, class U, class R = std::common_reference_t<deref_t<T>, U&&>>
constexpr auto reference_or(T&& m, U&& u) -> R;   // R usually a reference; dangling static_asserts

template <nullable T, class U, class R = std::common_type_t<deref_t<T>, U&&>>
constexpr auto value_or(T&& m, U&& u) -> R;       // R usually a value

template <nullable T, class I, class R = std::common_type_t<deref_t<T>, std::invoke_result_t<I>>>
constexpr auto or_invoke(T&& m, I&& invocable) -> R;  // forward<I>(invocable)() only when disengaged

template <class Ret = void, nullable T, class... Args,
          class R = std::conditional_t<std::is_void_v<Ret>, std::remove_cvref_t<deref_t<T>>, Ret>>
constexpr R or_construct(T&& m, Args&&... args);   // + initializer_list overload
#+end_src

Every engaged path is ~static_cast<R>(*std::forward<T>(m))~: an rvalue
optional/expected moves its payload; pointers and optional<T&> copy.

Member half, in the vendored include/beman/optional and include/beman/expected:
value_or_construct(args...), value_or_construct(il, args...), value_or_else(f),
each const& and &&; return remove_cv_t<T> on optional (as its value_or does,
LWG4406) and T on expected; remove_cv_t<T> and const-only on the T&
specializations.

C++23 floor for the paper: reference_constructs_from_temporary_v. The
header polyfills it over the compiler builtin, so it builds at C++20 and on
MSVC.

* Findings from the test build-out (harvested into the paper)

- expected<T,E> models nullable — bool(e) and *e both valid on const
  expected (handoff 002). Error-discarding is by design; documented.
- const-qualified concept is observable behavior: nonconst_nullable (both
  ops, non-const) rejected. Framed in Design as "observation is a query".
- Function pointers: the minimal concept ADMITS them (bool + deref both
  valid); P1255's nullable_object excludes via is_object of the referent.
  Open question for LEWG; do not claim they're excluded.
- R0: iter_reference_t<T> computed from T&, so rvalue nullables never
  moved their payload — the "observe, don't consume" rule, with the
  decltype(*forward<T>(m)) alternative flagged for LEWG (handoff 003).
  R1 (2026-09) adopted the alternative: deref_t<T> carries the value
  category, rvalue optional/expected move, pointers and optional<T&> copy.
  The axis is containment (is the payload a subobject?), not ownership —
  unique_ptr owns and still yields T&, because ownership there is the
  deleter's policy. rvalue_nullable.test.cpp copy/move-counts the engaged
  path for all four models so the split is test output.
- common_type results table (handoff 003) and common_reference const-
  propagation table (handoff 004) are reproduced in the paper.
- value_or fallback confirmed eager (lambda counted while engaged);
  or_invoke laziness is the step-05 suite.
- Dangling rejection example verified: reference_or(opt, 0) →
  common_reference_t<int&, int&&> = const int& → binds temporary →
  static_assert fires (handoff 004).
- No header bugs found through step 03 (26/26 tests green).

Final-suite findings (steps 04-07, 59/59 green, plan complete):
- SURPRISE (handoff 005): common_reference of unrelated lvalue refs need
  not be a reference. common_reference_t<int&, long&> = long;
  common_reference_t<string&, const char(&)[N]> = string. reference_or
  then compiles, guards vacuous (R not a reference), returns a prvalue —
  value_or behavior under a reference_or name. New LEWG question in the
  paper: mandate R is a reference type?
- SURPRISE (handoff 006): or_invoke + reference-returning invocable
  decays via common_type → value. Lazy-reference quadrant of the family
  is empty; paper says deliberately so, reference_invoke composable later.
- Confirmed: all three constexpr in constant evaluation (optional,
  expected, raw pointers); optional<T&> rebinding semantics tracked by
  value_or/reference_or; negative-compile harness self-validated by
  mutating the expected-diagnostic regex.

* or_construct — LANDED, folded into the paper (2026-06-12)

The sibling plan (tmp/test-plan-or_construct/) completed: both overloads
in the header, 106/106 tests, no header bugs. Surface as resolved by
Steve:
- ~or_construct<Ret = void>(m, args...)~ + initializer_list overload.
- Default R = remove_cvref_t<deref_t<T>> (iter_reference_t in R0) — the
  decayed payload type. INWARD conversion, deliberately unlike value_or's outward
  common_type: there is no fallback value to common with, only
  constructor arguments. The member function's model, correct here.
- Leading explicit ~Ret~ (void sentinel via conditional_t) lets the
  caller name the constructed type — or_construct<string>(m, ...) —
  something P3413's member cannot offer.
- Direct-initialization: explicit ctors usable. Always a prvalue;
  cannot dangle. With optional<T&>, result is a value, never a
  reference.
Paper updated: Design intro listing (four functions), new Design section
"or_construct: the fallback as constructor arguments", quadrant text,
P3413 chapter prose + table row + closing ("overlap is now total"),
Implementation Experience (106 tests, arities, laziness), Proposal
(four functions; or_construct vs value_or_construct in the names poll),

* Decided in R1 (was: open questions, R0 polled nine)

LEWG answers few questions well and none quickly; R1 decides all but one
and states the decisions in Proposal, to be revisited only if LEWG
disagrees.

- Dangling guards are /Mandates/ (static_assert), not constraints: a
  dangling call is a bug to diagnose, not a candidate to drop.
- Names: reference_or (not ref_or — the library prefers unabbreviated),
  or_invoke (or_else is taken and re-wraps; the member half keeps P3413's
  value_or_else, and the two differ in return type deliberately),
  or_construct beside member value_or_construct.
- Plain constrained function templates, not CPOs: nothing to customize —
  the semantics are fixed by the protocol. They do not inhibit ADL.
- Header <optional>, freestanding. Feature macro __cpp_lib_value_or; the
  members bump __cpp_lib_optional and __cpp_lib_expected.
- expected<T,E> models nullable and value_or discards the error, by
  design; no error-observing overload.
- nullable is a public, named concept (R0 proposed exposition-only and a
  poll); semantics stated in words in the wording.
- The concept stays minimal: no is_object_v on the referent, so function
  pointers model it and are rejected downstream by common_type.
- An rvalue nullable moves its payload (see the findings entry above).

** Still open, the one ask to LEWG
Whether reference_or should mandate that the computed common reference
/is/ a reference type. As specified it degrades to a prvalue for unrelated
types (common_reference_t<int&, long&> is long), the guards are vacuous,
and a caller who wanted a reference gets a copy.

** yield_if / fate of P1255 — RESOLVED in R0
P1255 is concluded; D4270 inherits its remaining deliverables (the concept
and the free functions). Range optional (P3168, C++26) supplanted
views::maybe and views::nullable — an optional IS the 0-or-1 view, and a
pointer gets there via `p ? optional<T&>(*p) : nullopt` (P2988).
yield_if(cond, value) is now spellable as `cond ? optional(value) :
nullopt`, itself a range; residual demand is comprehension-pipeline sugar,
a small separate paper if experience warrants. Stated in the paper's
"What about yield_if, and the end of P1255" section.

** exposition-only vs named public concept — decided public in R1
For naming: it's vocabulary — P2988 forecast "concept std::maybe", P1255 is
"a concept to constrain maybes", users re-derive it divergently otherwise,
testable and appears in diagnostics. Against: a named concept is forever;
boolean-testable is the precedent for staying exposition-only. R0 went
exposition-only on the asymmetry (promotion is non-breaking). R1 reverses:
boolean-testable is plumbing for other concepts where nullable is the
thing users want to write down, and with P1255 concluded there is no
coordination to wait on. LEWG can take the name back at the cost of the
spelling.

** nullable concept details
- Requirements are on const remove_reference_t<T>&: types with only
  non-const operator bool / operator* do not model nullable. R0 spelled it
  const T, which discarded the const for a deduced lvalue reference and so
  did not enforce this; fixed in R1.
- Iterators excluded (no contextual bool). Function pointers ADMITTED by
  the minimal concept (bool + deref both valid) and rejected downstream
  when common_type fails; P1255R13's nullable_object would exclude them at
  the constraint via is_object. Kept minimal on purpose.
