* Rulings made during review

These are decisions taken in review that later edits should respect.

- The in-paper change list records *design* changes between revisions,
  not commits. Reorganizing where the member functions appear in the
  paper is presentation, and is not listed. Folding P3413R0's members in
  is one entry; the =optional<T&>= coverage rides inside it.
- The paper is written from after the merge. P3413R0 was a separate
  paper; it is not one now. Prose that treats it as live, competing, or
  "also carried" is a defect.
- The rvalue rule is argued from *containment*, not ownership. =unique_ptr=
  ordinarily owns its referent, and still yields =T&= from =operator*=
  whatever its value category, because ownership there is the deleter's
  policy and the referent is never a subobject. The axis that predicts
  =operator*= is whether the payload is a subobject.
- Where the member wording and the vendored reference implementation
  disagree, the wording conforms to the implementation ("I might as well
  conform to my own code"). The =optional<T>= members return
  =remove_cv_t<T>=, as its =value_or= does there.

* Findings still open

** W1. Free-function Effects dereferenced an lvalue — FIXED (this branch)
Every free-function /Effects/ in the Wording chapter read
=static_cast<R>(*m)=. =m= is a named parameter, so =*m= is the lvalue
dereference, which for =optional= and =expected= yields =T&= and copies.
The design (Value categories), the change list, the implementation, and
the return type (computed from =deref-t<T>=, which is =T&&= for an rvalue
=optional=) all say the rvalue path moves. The words did not. All five:
=reference_or=, =value_or=, =or_invoke=, both =or_construct=. The
Implementation Experience listing, presented as the header "less the
portability shims", had the same =*m= and so was not the header.
Fixed: =static_cast<R>(*std::forward<T>(m))= in all ten places.
Check: =grep -n 'static_cast<R>(\*m)' papers/free_value_or.tex= is empty.

** W2. =deref-t= was used but never defined — FIXED (this branch)
The synopsis and every itemdescr used =@\exposid{deref-t}@<T>=; nothing
introduced it. Fixed: the synopsis now opens with
=template<class T> using deref-t = decltype(*declval<T>()); // exposition only=
and a paragraph says what it yields for an lvalue =optional=, an rvalue
one, and a pointer.

** W3. Member return type disagreed with the implementation — FIXED (this branch)
The =optional<T>= primary-template member wording returns =T=; the vendored
=beman.optional= returns =remove_cv_t<T>= for =value_or_construct= and
=value_or_else=, matching its =value_or=. The paper's own =optional<T&>=
wording already returns =remove_cv_t<T>=. =expected<T,E>= returns =T= in
both wording and implementation, and =expected<T&,E>= returns
=remove_cv_t<T>= in both; those stay.

The ruling is to take https://eel.is/c++draft/ as the standard. From the
review container both eel.is and the timsong-cpp.github.io mirror are
denied by the network egress policy, and the proxy's own guidance is to
report a denial rather than route around it, so [optional.observe] was
not read for this record.

Local evidence, for whoever reads it: commit bc9bda0 in the vendored
=beman.optional= ("optional::value_or return statement is inconsistent
with Mandates", LWG4406, https://cplusplus.github.io/LWG/issue4406) changed
the primary template's =value_or= to return =remove_cv_t<T>=, and 460fce5
gave the new members the same return type. If [optional.observe] reads
=constexpr remove_cv_t<T> value_or(U&& v) const &;=, the member wording
should say =remove_cv_t<T>= too, with Mandates
=is_copy_constructible_v<remove_cv_t<T>>= / =is_move_constructible_v<remove_cv_t<T>>=
and =is_constructible_v<remove_cv_t<T>, Args...>=, and the /Effects/
casts adjusted. If it reads =T=, the vendored members should go back to
=T= and the reason recorded. One reading of [optional.observe] settles it.

Ruling: conform to the vendored implementation. Done: the six =optional<T>=
member declarations return =remove_cv_t<T>=; each itemdescr introduces
=X = remove_cv_t<T>=, Mandates =is_convertible_v<const T&, X>= (const&) or
=is_convertible_v<T, X>= (&&) plus the construction or invoke requirement
on =X=, and Effects use the =if=-form the implementation uses. The Design
chapter and the comparison table now say "what =value_or= beside them
returns" rather than =T=. =expected= unchanged. A later read of
[optional.observe] should confirm the draft agrees; if it does not, that is
an implementation question, not a wording one.
